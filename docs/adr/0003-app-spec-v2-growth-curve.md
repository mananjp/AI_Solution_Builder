# ADR 0003: AppSpec v2 Contract & Non-Destructive Codegen

- **Status**: Accepted
- **Date**: 2026-10-01
- **Feature**: AppSpec v2 & Non-Destructive Code Generation
- **Deciders**: Engineering & Architecture Team

---

## Context

Legacy MVP generation relied on static template copying with hardcoded mock text (e.g. hardcoded vanilla/chocolate strings or dummy user tables). When users modified generated frontend pages and re-triggered builds, the system would overwrite user changes or fail to reconcile schema differences.

Furthermore, applications have distinct operational stages and data storage requirements that were not modeled in the original `AppSpec` v1 contract.

---

## Decision

We expanded `AppSpec` to **v2** and established non-destructive generation patterns:

1. **AppSpec v2 Domain Model**:
   - `app_kind`: Categorizes app typology (`landing_page`, `crud_internal`, `dashboard_analytics`, `workflow_automation`, `marketplace_ecommerce`).
   - `lifecycle_stage`: Defines maturity (`prototype`, `mvp`, `production_ready`).
   - `data_layer`: Models persistence strategy (`mock_in_memory`, `sqlite_local`, `postgres_relational`, `stateless`).
   - `theme`: Captures primary, secondary, accent, neutral, and surface palettes, plus dark mode preferences and border radii.
   - `analytics`: Configures opt-in KPI tracking, event tracking, and chart dependencies.
   - `seed_data`: Declares dynamic domain records tailored to the user's prompt (e.g. specific ice cream products, services, appointments, catalogue items).

2. **Non-Destructive File Generation**:
   - Every generated frontend file receives a header stamp: `// @generated by AI Solution Builder`.
   - Before overwriting existing files during subsequent builds, codegen inspects the target file.
   - If the stamp is missing or the file has been modified by the developer, the new generation is written to an adjacent sibling file (e.g. `page.generated.tsx`) and the original file is preserved.
   - `plan_schema_delta`: Computes additive and destructive differences between schema revisions, allowing safe database migrations without dropping custom columns.

3. **Dynamic Template Parameterization**:
   - Removed all hardcoded copy from code generator templates.
   - All components and pages now dynamically bind to `spec.entities`, `spec.seed_data`, and `spec.theme`.

---

## Consequences

### Positive
- Developers never lose hand-crafted UI improvements or custom API integrations on subsequent builds.
- Dynamic data binding produces realistic, bespoke MVPs matching the prompt instead of generic boilerplate.
- Clear migration paths for evolving data models over time.

### Limitations & Trade-offs
- Developers must inspect `.generated.tsx` files when reconciling major structural rewrites.
